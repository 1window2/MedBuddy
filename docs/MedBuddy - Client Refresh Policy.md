# 클라이언트 조회·갱신 정책

홈, 채팅, 일정, 위젯에서 같은 작업을 반복하지 않도록 조회와 표시 갱신을
구분한다. 복용 기록의 영속 저장, 계정별 권한 검사, 실패 후 재전송은 유지한다.

## 보호자 홈과 알림 감시

- 홈과 위젯은 `GET /caregiver/schedules`로 활성 연결의 별칭, 알림 설정,
  오늘 복약 일정을 한 번에 받는다. 알림을 끈 환자도 포함하며 저장 약 상세는
  요청하지 않는다. 환자 상세 화면의 기존 조회 API는 유지한다.
- 서버는 인증된 보호자의 활성 연결만 조회한다. 클라이언트도 응답의 보호자,
  연결 상태와 환자 범위를 확인하고, 홈에서 전달한 연결 목록과 교집합을 사용한다.
- 같은 로그인 세션의 홈과 전경 알림 감시는 `CheckCaregiverMedication`을
  공유한다. 진행 중인 홈 조회를 합치고, 감시는 같은 날의 성공한 홈 응답을
  15초 미만 동안 재사용한다. 홈의 명시적 새로고침은 새 요청을 수행한다.
- 홈 응답이 없거나 만료되면 감시는 기존 `/caregiver/monitoring`을 이용한다.
  이 API는 알림이 활성화된 환자의 일정만 조회하는 정책을 유지한다.
- 계정 변경·폐기·조회 실패·날짜 변경 후에는 이전 성공 결과를 재사용하지 않는다.
  백그라운드 작업이나 다른 프로세스까지 공유하는 전역 캐시는 아니다.

서버 내부도 환자별 반복 조회 대신 저장 약과 완료 기록을 일괄 조회한다.
1~400명 범위에서는 연결·알림 설정·저장 약·완료 기록을 최대 네 번 조회하며,
그 이상은 400명씩 나누어 DB 매개변수 제한을 피한다. 일정 응답에 필요한 열만
읽고 기존 복용 기간·시간대·진행률 응답은 유지한다. 홈의 연결 목록 조회는 남아 있다.

## 채팅 수신과 누락 복구

- 실시간 연결과 이력 조회가 정상이면 12초 주기 이력 조회를 멈춘다.
- 연결 장애 또는 이력 복구 실패 중에는 전경의 현재 대화방에서만 12초 간격으로
  다시 조회한다. 재연결 시도가 반복되어도 기존 조회 주기를 뒤로 미루지 않는다.
- 앱이 백그라운드로 이동하면 반복 조회와 실시간 연결을 중지한다. 화면 복귀나
  재연결 때 이력을 확인하고, 마지막으로 확인한 메시지까지 이어서 읽는다.
  누락분이 한 페이지인 50개를 넘으면 이전 페이지도 조회한다.
- 동시에 시작한 이력 조회는 하나로 합친다. 조회 중 복귀·재연결이 발생하면
  완료 후 한 번 더 확인한다. 메시지 병합 시 중복과 기존 읽음 상태를 보존한다.
- 소켓에는 30초 ping 간격을 설정해 응답 없는 연결도 장애로 감지한다.
- 메시지 입력은 작성 행에서만 갱신한다. 글자를 입력할 때 메시지 목록을 다시
  만들지 않으며 전송 버튼 활성화, 기존 초안과 읽음 위치는 유지한다.
- 대화 목록의 미확인 개수는 기존 활성 15초 갱신과 진입·복귀 때 조회한다.
  대화 안의 읽음 처리는 최신 위치가 보일 때만 수행하며, 알림 재진입은 초안을
  유지한 채 누락분을 확인하고 최신 위치로 이동한다. 상세 계약은
  [채팅 읽음·알림 진입](Chat%20Read%20State%20and%20Notification%20Entry.md)을 따른다.

서버의 일반 채팅 전송 보장은 [채팅 전달 설계](MedBuddy%20-%20Durable%20Chat%20Delivery.md)를
따른다. 기존 보호자 완료 Outbox가 만든 자동 채팅은 직접 실시간 방송하지 않으므로
화면 복귀·재연결·보완 조회 때 확인된다. 모든 서버 생성 메시지가 열린 대화방에
즉시 나타난다고 보장하는 변경은 아니다.

## 일정과 로컬 알림

- 방문했던 일정 탭으로 돌아올 때만 최근 15초 미만의 성공한 일정·알림 설정을
  재사용한다. 직접 새로고침은 재조회하고, 복용 상태 변경과 날짜 변경은 최근
  조회를 무효화한다. 실패를 성공한 빈 일정으로 취급하지 않는다.
- 동시에 진행되는 일정 새로고침은 합치되, 일정 조회 오류 화면의 명시적 재시도는
  별도 알림 설정 조회가 끝나지 않았어도 허용한다.
- `NotificationService`는 계정·시간대별로 날짜별 예약 계획을 저장한다.
  실제 기기 예약과 원하는 계획을 비교해 불필요해진 예약은 지우고, 새 예약이나
  시간·제목·언어·본문이 달라진 예약만 갱신한다.
- 동일한 예약은 다시 만들지 않아 사용자가 미룬 알림을 유지한다. 예약·미루기·
  취소는 같은 서비스 안에서 순서대로 처리하고, 대기 중 계정이 바뀌면 적용하지 않는다.
  기존 14일 예약 범위와 백그라운드 보충 작업은 유지한다.
- 본인 위젯은 오늘 완료된 시간대를 기기 저장 상태에서 확인하고, 계정·날짜·시간대가
  같은 예약·재알림과 미래 알림함 항목만 취소한다. 서버 응답 전과 오프라인에서도
  적용하며 다른 날짜·시간대 및 보호자 알림은 유지한다. 계정 변경을 다시 검사하고,
  취소 실패는 복용 기록을 되돌리지 않고 다음 위젯 발행 때 재시도한다.

## 홈과 위젯 표시

홈은 채팅 목록의 로딩 상태만 바뀌면 다시 그리지 않는다. 연결 목록, 별칭,
오류 또는 일정이 바뀌었는지 확인하고, 같은 환자 캐시·위젯 설정의 반복 발행을
줄인다. 저장된 홈 표시 설정이 늦게 복원되어도 조회 대상과 위젯 출처를 함께
바꾸며, 출처 변경이나 환자 캐시 발행 실패 후에는 다시 발행할 수 있다.

복용 기록은 기기의 암호화 저장소에 먼저 저장한다. 이후 `DoseSyncService`의
표시 콜백은 여러 변경을 합쳐 최신 상태를 발행하며 서버 전송을 기다리게 하지
않는다. 표시가 늦거나 실패해도 저장된 복용 기록을 실패 처리하지 않는다.
기존 작업 ID, 전송 순서, 중복 방지 및 서버 확인 전 전송 대기 표시는 유지한다.

## 처방 약 상세조회

처방 약 상세조회는 기존 여섯 건 동시 요청을 유지한다. 계정 잠금 때문에 서버가
명시적으로 반환한 `503 This account is busy`에 한해 `Retry-After`의 남은 대기
시간 뒤 순차적으로 한 번 재시도한다. 대기는 1~30초 범위이며 헤더가 없으면
5초를 사용한다. 다른 503은 자동 재시도하지 않으며, 화면 종료·새 분석 후의
응답이나 재시도는 이전 처방에 적용하지 않는다. 인증·호출 제한·삭제 표식 검사는
유지하되 공개 약품 조회는 계정 등록 직후 연결을 반환한다. 독립 카탈로그 작업이
같은 연결 풀을 기다리는 동안 요청이 다른 연결을 붙잡지 않는다. 사용자 데이터
저장 경로의 계정 잠금 정책은 유지한다.
후보 확인과 원문 보존은 [약명 매칭 계약](Medication%20Matching%20Review.md)을 따른다.

## 병원·약국 지도

선택·즐겨찾기·검색 결과가 바뀌면 해당 마커만 제거·추가하고 나머지는 유지한다.
네이티브 마커 작업은 순서대로 처리하며 대기 중 변경은 최신 결과로 합친다.
이름·좌표가 같아 마커를 유지해도 탭 시에는 최신 영업시간·연락처를 전달한다.
사용자가 직접 지도를 움직이거나 선택을 해제하면 대기 중인 자동 이동은 취소한다.

## 사진 처리

처방전 촬영 이미지의 방향 보정·자르기·JPEG 변환과 직접 등록 사진의 크기 조절·
압축을 별도 isolate에서 처리한다. 처방전 원본 임시 파일 정리 규칙은 유지하며,
직접 등록 사진은 기존처럼 긴 변을 최대 1600px로 저장한다. 복약함과 본인·보호자
일정 목록의 작은 사진은 표시 크기에 맞춰 디코딩 크기를 제한한다.

이 변경은 화면을 그리는 실행 흐름의 이미지 처리 부담을 줄인다. 외부 분석 API의
응답 속도나 실제 처방전 인식 정확도가 향상되었다는 의미는 아니다.

## 배포와 검증

새 앱은 `/caregiver/schedules`가 있는 백엔드와 함께 배포한다. DB 스키마 변경은
없다. 기존 API는 유지하지만 새 앱을 이전 백엔드에 연결하면 보호자 홈 조회가
실패하므로 백엔드를 먼저 갱신한다.
