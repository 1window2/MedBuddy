# MedBuddy v0.2.0-beta Stabilization Candidate

## Status

- Candidate version: `0.2.0+21`
- Stable baseline: `v0.1.1-beta`
- Preparation branch: `beta/v0.2.0`
- Target tag: `v0.2.0-beta`
- Platform: Android
- Publication status: limited off-Play pre-release through GitHub, by owner
  decision on October 8; no Google Play distribution is planned for now

This document records the candidate boundary and its gates. The GitHub
pre-release notes carry the final commit identifiers and signed artifact
checksums.

## Limited Pre-release Decision — 2026-10-08

The owner decided to merge `beta/v0.2.0` into `main` and publish
`v0.2.0-beta` as a GitHub pre-release for a limited group of direct-install
testers. This is a decision to proceed with the gates below still open, not a
statement that they passed:

- Firebase App Check stays disabled under the off-Play exception. The signed
  workflow refuses that exception on `main`, so the published APK and AAB are
  built from the final `beta/v0.2.0` commit, whose tree is identical to the
  merge commit on `main`. The AAB is built with App Check enabled and is not
  usable until Play distribution and enforcement are set up.
- Two-device checks (caregiver linking, chat, push delivery, missed-dose
  alerts) have not been performed on physical devices. Validation used one
  Android 12 phone and one account.
- The corrections from the October 7 audits are covered by automated tests;
  only installation, data preservation, schedule actions, dose synchronization
  and read-aloud were exercised on the phone.
- The product limits recorded in
  [the full code sweep](../qa/v0.2.0-architecture-gates.md#full-code-sweep--2026-10-07)
  remain, notably that non-daily directions are stored as daily counts.

## Stabilization Boundary

As of October 5, v0.2.0 is in cleanup and release preparation. Do not add new
features, integrations, dependencies, migrations or user workflows to this
candidate. Tidy existing code, remove proven obsolete code, reduce duplication
and keep ownership and pipeline steps clear. Preserve established behavior,
API/storage contracts, medication safety checks and release/security gates.

Keep cleanup batches bounded and independently reviewable. Pull the shared branch
before work and before committing, run the affected regressions and full backend /
Flutter checks, then commit and push on `beta/v0.2.0`. Maintain related UML sources
and rendered assets when responsibilities or class/module ownership move. Do not
create replacement branches, rewrite shared history or change the app version /
dependency lockfile as a cleanup side effect.

Acceptance-blocking defects discovered during cleanup must be recorded and
triaged explicitly; do not hide behavioral changes inside a refactoring commit.
New product ideas belong to the post-v0.2.0 backlog. The owner-authorized candidate
`866db67` passed exact-source CI and protected signing, then was installed as a
verified matching-signer update on one synthetic Android 12 phone. See
[the candidate evidence](../qa/v0.2.0-map-direct-filter-device-validation.md#signed-candidate-update--2026-10-05).
The later cleanup and visual candidate `2d85e6e` replaced it on October 7 with the
same gates, followed by the audit-corrected candidate `e328bab`; see
[the evidence](../qa/v0.2.0-map-direct-filter-device-validation.md#final-candidate-update--2026-10-07).
Physical acceptance remains incomplete, including an unexplained notification
unread-state difference. Google Play / App Check and two-device checks remain
open, not waived by feature freeze.

## Frozen Candidate Scope

- Consistent schedule-based headers, typography, compact descriptions and action
  styles across primary screens, with large-text layout regression coverage.
- Shared medication registration and photo-source menus, explicit save/cancel for
  schedule reminder edits, and visible-result selection for cabinet bulk deletion.
- Direct medication entry with schedule review and optional app-owned images.
- Bounded multi-pill identification with explicit per-pill confirmation,
  partial-failure recovery, and duplicate schedule handling.
- Nearby-pharmacy lookup from the home screen with backend-held credentials, map and
  list synchronization, named markers, content-sized collapsible map details,
  favorites, freshness status, and safe external routes. Detail-sheet actions
  preserve map exploration and access to the pharmacy list.
- Patient-caregiver medication chat with active-link navigation, authorized medication and
  pharmacy context, idempotent messaging, read state, and schedule actions.
- Nearby-hospital search with specialty selection before GPS/API work, bounded
  radius expansion, date and consultation filters, visible incomplete-data
  handling, and server-verified hospital cards shared through linked chat.
- Chat unread boundaries, recipient read receipts, role-aware notification entry
  and transactional notification jobs with retry. The backend requires migration
  `b3a7d9e2f601` before starting the current worker.
- Pharmacy calendar outages preserve location results and report opening status
  as unverified instead of assuming ordinary weekday hours.
- Selected chat deletion: private deletion at any age, or sender-only shared
  redaction within 24 hours, without modifying medication records.
- All completed v0.1.1 medication, reminder, caregiver, camera, privacy,
  authentication, accessibility, and HTTPS hardening retained as the baseline.

## Remaining Release Gates

- Signed builds from `main` require App Check enforcement. The off-Play APK
  exception is restricted to the active beta branch; public Play Integrity
  configuration and matching backend enforcement still require acceptance.
  Protected builds now additionally verify live Firebase certificate
  registration and the reviewed Play Integrity verdict policy before signing
  secrets are restored. Read-only federation and the Play app-signing
  fingerprint still need owner setup. Google Play developer enrollment is
  deferred by the owner as of October 2; no enforcement setting was changed.
  Protected releases default to a Play-only AAB; direct APK output requires an
  explicitly selected dual-channel policy and matching Play/APK signing keys.
  The temporary off-Play beta retains separate APK/AAB artifacts.
  See [the preflight prerequisites](../Production%20Deployment.md#protected-android-app-check-preflight).
- The signed-build workflow first requires successful `push` runs of both
  `backend-ci.yml` and `frontend-ci.yml` for its exact source commit. A pending,
  failed, missing, or unavailable check blocks the secret-bearing signing job.
  Wait for CI to finish and rerun the workflow; do not bypass this gate.
- Pharmacy is available from home and chat is shown for active links. Complete
  their privacy, authorization, and two-device checks before public release;
  navigation visibility is not an authorization boundary.
- The September 30 production backup was restored into an isolated PostgreSQL
  database, and the restored snapshot migrated to the single Alembic head.
  The matching backend revision is deployed; the shared catalogs are populated.
  Recheck these gates against the final release commit and assess catalog
  freshness before signing.
- The live ingress allowlist includes hospital routes and `/ready/catalogs`.
  Pharmacy, hospital, and chat reach the JSON authentication boundary; public
  catalog readiness returns JSON HTTP 200, and unknown API paths remain blocked.
  The signed workflow repeats these checks. See
  [the rollout evidence](../qa/v0.2.0-2026-09-30-production-rollout.md).
- The September 30 production hospital probe received HTTP 403, reason code `30`.
  Hospital-service approval and bounded location, detail and specialty-list
  responses passed on October 1 through the deployed parser using its existing
  shared key. Specialty and open-at-time searches with the real calendar
  dependency also passed through the deployed control. The upstream access
  blocker is closed; authenticated client acceptance and provider outage/quota
  checks remain open. No secret change, deployment or restart was required.
  See [the provider approval follow-up](../qa/v0.2.0-2026-10-01-hospital-provider-approval.md).
- Pass backend tests, Flutter analysis and tests, Android release compilation,
  dependency/security checks, and release-metadata validation.
- Diagnose the unexplained first health-recommendation failure observed in
  [the October 5 contributor emulator checks](../qa/v0.2.0-2026-10-05-refactor-validation.md).
  Subsequent successful generation/cache/retry checks do not close its cause.
- Diagnose the notification unread-state difference observed across the signed
  update. Four historical inbox rows remain visible, but the baseline badge of
  four is absent on the candidate; complete read-state preservation is unproven.
- Validate incremental map-marker recovery if a native addition fails after
  applying only part of the requested markers. Synthetic queue regressions now
  exercise the corrected recovery path, but native device acceptance remains open.
- Install the final signed build on physical devices and verify standalone
  HTTPS startup, authentication, core medication flows, update preservation,
  network transitions, caregiver linking, and push delivery.
- Publish the tag, release notes, artifacts, and checksums only after those
  gates have evidence tied to the final `main` commit.

## Merge Discipline

The preparation branch contains the completed `main` history through the
v0.1.1 baseline as normal Git ancestry. Continue v0.2 work on
`beta/v0.2.0`; do not rebase or force-push the shared branch. The rule not to
merge into `main` until the remaining gates pass was set aside by the owner on
October 8 for the limited pre-release described above; the open gates still
apply before any public or Google Play release.
