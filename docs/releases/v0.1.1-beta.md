# MedBuddy v0.1.1-beta Release Candidate

## Status

- Candidate version: `0.1.1+12`
- Stable baseline: `v0.1.0-beta`
- Preparation branch: `beta/v0.1.1`
- Target tag: `v0.1.1-beta`
- Platform: Android
- Publication status: not yet published

The final release commit and artifact checksums must be added to the GitHub
release when the candidate is published. Until then, this document describes
the intended contents and the remaining verification boundary.

## Included Maintenance Changes

- Stabilize compact and large-text layouts, settings navigation, health
  recommendation safe areas, and English home text.
- Prevent stale schedule requests from controlling current loading state and
  dismiss medication-completion feedback without leaving stale UI state.
- Preserve OCR rows and verified medication results during partial lookup
  failure, allow recovery of omitted rows, and retain public medication detail
  fields in normalized responses.
- Keep caregiver notification labels useful without exposing internal patient
  hashes.
- Release local SQLite startup write locks after account registration while
  retaining PostgreSQL transaction-scoped account locking in production.
- Stabilize prescription-camera rotation and crop captured images to the same
  guide rectangle shown to the user.
- Display the application version in Settings and advance Android metadata from
  `0.1.0+11` to `0.1.1+12`.

No v0.2.0 pharmacy, linked-chat, direct-entry, or multi-pill batch feature is
part of this maintenance release.

## Automated Verification

Every release-candidate commit must pass:

- FastAPI import and the complete backend test suite on Python 3.11.
- Clean PostgreSQL Alembic upgrade, downgrade, and re-upgrade.
- Flutter dependency resolution, static analysis, and the complete unit/widget
  suite on the pinned Flutter SDK.
- Compile-only Android release APK construction.
- Code scanning and dependency checks required by the protected main-branch PR.
- `python3 scripts/check_release_metadata.py` for version, documentation, and
  signed-workflow consistency.

The protected signed workflow remains restricted to `main`; release secrets
must not be exposed to the preparation branch or ordinary pull requests.

## Deferred Device Verification

No Android physical device is currently available. Physical-device and
two-device checks are therefore deferred, not passed or waived. This accepted
deferral does not block the v0.1.1 publication decision. The unchecked source
of truth remains
[`docs/qa/beta_accessibility_device_regression_checklist.md`](../qa/beta_accessibility_device_regression_checklist.md).

The deferred pass must use the published release candidate or record any
additional fix followed by a new signed artifact. Priority cases are
portrait/landscape camera cropping, TalkBack, reboot and alarm persistence,
data-preserving app update, Wi-Fi/cellular transitions, battery saver, and
patient-caregiver push behavior.

## Publication Procedure

1. Freeze `beta/v0.1.1` and open a reviewed pull request to `main`.
2. Require backend, PostgreSQL migration, Flutter, Android compile, release
   metadata, code-scanning, and dependency checks to pass.
3. Merge the reviewed candidate into `main` without introducing unrelated
   feature work.
4. Deploy the matching backend revision and confirm `/health` and `/ready`
   report the expected API contract.
5. Run the protected signed Android workflow from `main`, verify the APK and
   AAB signing fingerprints, and preserve their SHA-256 files.
6. Tag the merged release commit as `v0.1.1-beta` and publish the artifacts,
   checksums, known limitations, and deferred-device status together.

## Merge Forward Into v0.2.0

After `v0.1.1-beta` is merged and published, update `beta/v0.2.0` by merging
the published `main` history. Do not replay or cherry-pick the same fixes again:

```bash
git fetch origin
git switch beta/v0.2.0
git merge --no-ff origin/main
git merge-base --is-ancestor v0.1.1-beta HEAD
git diff --check v0.1.1-beta..HEAD
```

The ancestry check is the authoritative proof that every published v0.1.1 fix
is present. File equality is not expected because v0.2.0 intentionally extends
shared modules, but conflict resolution must preserve both the published fix
and the v0.2.0 feature behavior. Run the complete backend, Flutter, migration,
and Android compile checks after the merge before resuming feature work.
