# MedBuddy v0.2.3-beta Development Line

## Status

- Candidate version: `0.2.3+24`
- Stable baseline: `v0.2.2-beta`
- Preparation branch: `beta/v0.2.3`
- Target tag: `v0.2.3-beta`, or `v1.0.0` if the line is published as the
  first public release
- Platform: Android
- Publication status: in development; distributed, like v0.2.2, as a limited
  off-Play GitHub pre-release when ready

This document records the candidate boundary. The GitHub pre-release notes
carry the final commit identifiers and signed artifact checksums.

## Scope

v0.2.3 collects small corrections and improvements found by reviewing the
released code and by using the app. The switches that belong to a public
release (Google Play distribution, App Check enforcement) are out of scope.

## Changes

A review of the released code by area (screens and copy, app logic, server)
found 50 defects; 49 are corrected here, and the remaining one is recorded in
the TODO.

### Server

- Daily limits end at midnight in Asia/Seoul; they ended at 09:00 local time
  while the refusal said "tomorrow".
- A hospital shared in chat counts against the hospital-search daily limit, and
  the medication lookup, which summarises approval records with the AI model,
  counts against the AI daily limit.
- The public hospital API budget is counted per provider operation, as the
  provider's quota is. A spent budget is answered with its own message and a
  wait until local midnight instead of "temporarily unavailable, retry in 5 s".
  The setting's upper bound allows an operating-account quota.
- An AI analysis reply that is not the agreed JSON is answered with 502 and a
  retry hint, not 400.
- Recording one medication as taken refuses a course that ended, has not
  started, or is on a rest day, as recording a whole slot already did.
- A dose recorded from chat by an app without dose-day schedules on a rest day
  of a weekly medication no longer fails with 500.
- A caregiver alert row that stalls repeatedly is given up after the attempt
  limit; a missed-dose alert that is no longer needed is recorded as given up,
  not as sent.
- The prescription change comparison reads bare durations and counts with the
  schedule's rules ("7" and "7일분" and "1주" are the same), and still reports
  added directions such as 식전/식후 or 필요시.
- A JSON request carrying a NUL character is refused with 422 instead of
  failing in the database; prescription text sent for analysis is capped at
  20,000 characters.
- Backend dependencies: FastAPI 0.142.2, Uvicorn 0.54.0, SQLAlchemy 2.1.3,
  Alembic 1.20.0, psycopg 3.3.6, google-genai 2.28.0, firebase-admin 7.7.0,
  python-dotenv 1.2.4 (from the grouped Dependabot proposal, without
  websockets 17, which google-genai does not allow yet).

### App behaviour

- A settings change made offline is kept and sent again; the next server read
  or a restart no longer brings the old value back (for example a reminder the
  user had switched off).
- A dose record the server rejects holds back only later records of the same
  dose; other days and slots keep uploading. A chat dose refused by the daily
  chat limit is sent without the chat link. The queue stops polling when
  nothing is left to send.
- Today's reminder is cancelled after a recorded dose regardless of the
  widget's configuration.
- A saved medication without a prescription date starts on its registration
  date in the medication box, as on the server.
- Dose amounts and durations are translated to English by one rule ("2
  tablets", "56 days").
- A chat notification preview never splits an emoji; delivery markers of
  caregiver alerts are pruned after 7 days; deleting a medication already
  deleted elsewhere succeeds.

### Second review

A second review covered the areas the first one did not focus on and the fix
commit itself; nine findings were corrected:

- Starting the app without a session (offline, or the server not answering)
  no longer erases the account stored on the device, so a caregiver's
  missed-dose alerts that arrive afterwards are shown again.
- A reminder action tapped while the app starts offline survives a sign-in
  retry and is carried out for the stored account only.
- Signing out unregisters the device's push token even when this run never
  managed to register it, so an earlier run's registration does not keep
  showing the ended account's pushes.
- A sign-out aborted by a failing local step starts push and dose upload work
  again for the account that stays signed in.
- A chat dose loses its chat link only for the daily chat limit, not for a
  short-term rate limit.
- The prescription change comparison reports frequency changes above four a
  day again.
- The medication lookup tells a used-up daily limit and a refused request
  apart from momentary load and an expired sign-in.
- The account export leaves out the display name the other participant set.
- A retried account deletion whose first answer was lost finishes instead of
  failing with 401 when the revocation check is on.

### Found without a device

- The home-screen widget no longer fails to load on Android 7 to 11; it used
  a call Android allows only from Android 12 (affected since 0.2.0).
- The safety note shown after recording a dose uses the full width at large
  text; its "View" button had taken most of the width.
- A medication lookup keeps the candidates whose AI summary succeeded when the
  summary of another candidate fails; the whole lookup used to fail (seen with
  a provider error on one of three "포사맥스" products in a synthetic
  prescription test). A medication without a summary is still not returned.
- A new home-screen widget starts at 4 x 1 instead of 4 x 3, which took more
  of the home screen than its content needs (374 dp tall on a Galaxy Note10).
  At one row it shows the slot, the save state and the dose button on one
  line; enlarged, it shows the date, details and slot paging as before.
  Widgets already placed keep their size.

### Screens and wording

- Errors: a refused request no longer asks to sign in again unless the server
  said the sign-in expired; an ended link, a wrong or expired or used link
  code, a used-up daily limit and the spent hospital budget each get guidance
  that says what to do; developer text is never shown (the status code is kept
  in the generic message).
- Opening a chat from a notification for a link that has ended says so and
  offers link management; an expired patient code is greyed out with a
  "new code" button; manual registration shows its save errors in the screen's
  language.
- Larger touch targets (dose toggle, save and close buttons, the link list's
  row buttons), larger text for shared pharmacy/hospital cards, chat times, tab
  labels and link roles; a tap on a row selects it in the medication box's
  selection mode.
- Undoing a whole slot on the home screen asks for confirmation; failure
  messages stay as long as success messages; times follow the 오전/오후
  setting everywhere; a read-aloud failure is reported; a permanently denied
  camera permission offers the system settings.
- Wording: "복약함" for the saved-medication screen, "연동" for the
  patient–caregiver link, "복용 완료 취소" for undoing a dose, "Caregiver
  alerts", "글자 크기" and "읽기 속도"; one date format (2026-10-01); the
  multi-delete confirmation names the count.

### Follow-up regression safeguards

- A medication lookup that loses some AI summaries keeps the successful
  candidates but requires the user's confirmation, even when only one remains.
  Partial results are not cached; the `drug_info:v2:` namespace also avoids
  reusing older, potentially incomplete candidate lists. This completeness
  check covers the candidates considered, not the entire medicine catalogue.
- Only one dose upload per account may hold an active lease. A delayed reply
  can no longer replace newer daily progress with an older snapshot. Expired
  leases remain retryable; blocked records still let unrelated doses proceed.
- Settings writes carry the server revision they were based on. Stale writes
  receive a conflict; only the latest pending intent retries. The app stores
  the preferences and their pending state together so an interrupted save,
  old read or late reply does not restore an earlier choice.
- Account deletion removes the new preference snapshot and synchronization
  metadata only for that account and only after successful server deletion.

The settings safeguard requires migration `ab29d71c4e60` and the updated
backend before distributing the matching app. Legacy clients remain supported
but do not gain protection against their own delayed writes. See
[Production Deployment](../Production%20Deployment.md) for rollout and rollback.
