# MedBuddy 1.0.0

## Status

- Version: `1.0.0+27` (server `1.0.0`)
- Stable baseline: `v0.2.5-beta`
- Preparation branch: `beta/v1.0.0`
- Target tag: `v1.0.0`
- Platform: Android
- Publication status: versioned for release on 2026-11-13 (signed build and server
  deploy); publishing it on GitHub as a pre-release or as the latest release is the
  owner's decision (see [the release TODO](../TODO.md))

This document records the release boundary. The GitHub release notes carry the
final commit identifiers and signed artifact checksums.

## Scope

The 1.0.0 line finishes what the beta lines left open: the code work, owner
decisions, owner actions and device checks listed in the release TODO.
New features enter only after a scope review.

The owner took the 2026-11-07 additions into the 1.0.0 scope (owner decision on
2026-11-07, after the review below): patient notification completion actions,
history sharing from chat, and medication search in standalone, manual-entry and
chat flows. This does not approve the production release or replace the remaining
device and deployment checks.

- Version `1.0.0+27`; the server reported `1.0.0-rc` until 2026-11-13 and `1.0.0`
  since.
- The signed workflow and its checks allow `beta/v1.0.0` in place of `beta/v0.2.5`
  for test builds. Builds from it keep the off-Play exception (App Check not
  enforced) until the distribution decision.

## Changes (2026-11-07)

- **Direct APK distribution:** replace the combined ARM APK with two standalone
  downloads, `app-armeabi-v7a-release.apk` (ARM 32-bit) and
  `app-arm64-v8a-release.apk` (ARM 64-bit). Install only the one supported by the
  device's Android ABI. CI builds and checks both; the signing workflow verifies
  each certificate and publishes each file with its own checksum. Both retain the
  same normal version code rather than Flutter's per-ABI version-code offsets.
  A published update still requires a higher build number and compatible signing
  certificate. Play AAB delivery, native maps and on-device OCR are unchanged.
  See [APK distribution](../../frontend/README.md#android-apk-distribution).
- **Caregiver check-request actions:** capable Android clients show a patient
  Taken action for today's structured caregiver slot-check request. The action
  durably queues the original dated dose in the existing encrypted outbox, checks
  account and schedule scope, and reuses idempotent sync. An ended link suppresses
  chat creation without discarding a valid patient-owned dose. Older clients keep
  ordinary notifications. Deploy capability migration `f7a2c9e4b610` after
  `e6b4d2a9f031` before the server and matching app; existing tokens default off.
- **Chat history sharing:** the composer opens period sharing for the conversation's
  patient, including caregiver entry, with the current active link as recipient
  and an explicit send confirmation. It does not grant history write access.
- **Medication search and references:** standalone search, manual-entry selection
  and chat selection share the existing lookup. Unsaved chat product references
  are display-only snapshots, separate from saved medication IDs; the combined
  attachment limit is ten and references cannot trigger dose actions. The server
  rebuilds each reference from the public product data its search returned in the
  last 24 hours (migration `a9d3c5e71f24`, no account data) and refuses others; the
  app then asks the user to search again.
- **Manual batches and intervals:** validate remaining entries, then save one at
  a time; retry skips entries already completed in the screen. Custom scheduled
  intervals accept 1–90 days. This is not an atomic or durable batch queue.
- **PRN refresh state:** an empty prior list remains loading during refresh;
  nonempty same-day data stays visible and failures are not treated as empty data.
- **Yesterday's list after midnight:** with the app left open across midnight, a tap
  on yesterday's list recorded today's dose and removed tonight's reminder of that
  slot. It is now refused: today's list is loaded and the user is asked to tap
  again. Reminder actions pass their own day and are unaffected.
- **Link codes:** two caregivers redeeming two codes of one patient at the same
  moment could pass the per-patient link limit by one. Redemption now locks both
  accounts before it counts. The lock is released with a commit, so an account row
  created by the same first request is kept.
- **Unlink:** locks both participants, so a chat message or caregiver setting
  written at the same moment cannot stay behind on the ended link. It also
  invalidates the patient's unused link codes: a removed caregiver holding another
  code issued before the unlink could otherwise link again without the patient.
- **Nearby pharmacy search:** a per-account daily quota
  (`PHARMACY_SEARCH_DAILY_LIMIT`, 200) keeps one account from spending the shared
  live pharmacy budget.
- **Chat stream and revoked sessions:** an open chat stream re-checks its ID token
  when it revalidates the link, so a revoked session or a disabled account stops
  receiving messages within about a minute instead of at the token's expiry.
- **Push after a password reset:** a device that kept a revoked session stops receiving
  chat previews and caregiver alerts once the owner signs in again on any device.
- **Prescription text:** a line longer than 500 characters is refused before the privacy
  check; one crafted 20,000-character line had stalled the whole server for about 8
  seconds per request. A full-length text now costs about 2 ms.
- **Pill photos:** the 100-scan JPEG limit from v0.2.5 also covers JPEGs with an MPF
  segment (format "MPO"), which had bypassed it. Photos are turned upright from the EXIF
  orientation tag alone; re-encoding the whole EXIF block let a small image with a large
  tag cost seconds of CPU.
- **Quotas:** pharmacy shares that need a live lookup count against the pharmacy
  search quota, and per-IP counters treat an IPv6 address as its /64. The per-IP daily
  count is taken only after sign-in, so unauthenticated requests no longer leave
  day-long counters that could fill the counter store.
- **Signed builds:** a requested API endpoint is shown before the signing approval,
  and the ingress probe compares the API contract header. The signing job downloads
  the pinned Flutter SDK and all packages instead of restoring a cache that ordinary
  push runs write.
- **Start-up checks:** production refuses two spellings of one setting, missing
  revocation or verified-email checks, and the Firebase Auth emulator variable.
- **Slot completion cards:** the server's message id for a slot completion card is
  reserved; a patient message using it had kept the card from being created.
- **Service key in errors:** pharmacy, holiday and emergency-pharmacy lookups no
  longer chain the httpx error, whose text holds the request URL with the key.
- **Korean UI:** English developer text from a failed check (for example a caregiver
  screen given a reply without its data) is replaced by the generic Korean message.
- **Database role:** an opt-in data-only role for the API and catalog jobs, provisioned
  by the migration (see Production Deployment).
- **CI:** Flutter CI runs the Android instrumented tests (home-widget layout and refresh)
  on an API 34 emulator; the release gate requires them with the rest of Flutter CI.
- **Start-up:** the Naver map SDK, which loads a 24 MB native library, starts after
  the first frame instead of before it, and map screens wait for that one shared start;
  the portrait lock comes from the manifest alone. Read-aloud binds the device speech
  engine on the first request through an app channel instead of `flutter_tts`, which
  bound it and read the whole voice list on the main thread at every launch and in
  every background widget or reminder task. On a Galaxy Note10 (release build, 24
  cold starts each) the median launch went from 378 ms to 336 ms and the Dart work
  before the first frame from 94 ms to 67 ms.
- **Request pipeline:** today's schedule is requested together with the settings at
  launch instead of after them (reminder settings and reconciliation still wait for
  the settings), and the first load no longer re-reads the dose store that
  initialization has just read. A first schedule-tab visit within 15 s reuses that
  launch data, as a revisit already did. The two simultaneous 14-day window reads
  share one request. Screen-owned API clients share one connection pool instead of
  opening a new TLS connection per visit, while closing a screen still aborts its own
  requests. The time-zone set loaded before the first frame is the 10-year one
  (Seoul only is used). Measured on the emulator with a local server: the launch
  schedule request starts 200–400 ms after the settings burst instead of 600–800 ms,
  and a first schedule-tab visit makes 1 request instead of 5.
- **Revocation check:** the server checks each ID token's signature and expiry locally
  and reuses an account's revocation state (disabled flag, sessions-valid-after time)
  for 30 seconds instead of asking Firebase on every request, which cost a Google round
  trip of about 0.25-0.35 s from Korea (owner decision). A revocation made in Firebase
  applies within 30 seconds; an account this server deletes is forgotten at once.
  Corrected on 2026-11-11: once the cache held 10,000 accounts, the clean-up of
  expired entries used an undefined name, so every authenticated request that missed
  the cache failed from then on. It now drops the entries expired at the lookup time.
- **Link polling:** the home screen's 15-second link refresh pauses while another
  screen covers it and runs at once, restarting its period, when home is shown again.
- **Background dose sync:** the 15-minute dose-sync job exists only while there is
  network work: a record waiting to be sent, a widget tap, or an installed widget
  without today's data. Each run ends by keeping it or removing it; the app start,
  pause and resume do the same, so devices updated from earlier versions lose the
  job they no longer need, and accounts not signed in remove theirs. Every path that
  queues a record (app, widget, notification button, and retrying a rejected record,
  which had no job before) still registers the one-off upload. A widget refresh that
  cannot read today's schedule (for example offline at midnight) keeps the retry until
  it succeeds. Before, every account started a background engine every 15 minutes.
  Checked on the emulator with WorkManager's database: an offline record keeps both
  jobs and is sent once when the network returns, after which the periodic job is
  cancelled; an offline day change shows "refresh today's schedule", keeps the
  retry, and the widget recovers and the job is cancelled once online.
- **Request bursts on the server:** on PostgreSQL a request now waits on the event loop
  for its account's turn and then for a database slot (the pool size minus one) before it
  registers, instead of waiting inside one of the 40 worker threads. Before, more than
  about 40 requests in flight (a few phones opening the app in the same moment) left every
  thread waiting for a connection or an account lock while the requests holding
  connections had no thread left to finish, so the whole server stalled until the 10 s
  pool or 5 s lock timeout and answered 503. The turn and the slot are given back after
  each piece of database work that leaves no transaction open, so hospital and pharmacy
  shares and AI lookups hold neither while they wait for the provider, and later database
  steps queue again. The PostgreSQL account locks are unchanged. Measured locally with pool 5 on PostgreSQL 16:
  48 requests at once p95 0.17 s instead of 10 s stalls with 503s, 96 at once p95 0.76 s,
  200 at once all answered within 4.5 s, and another account's requests no longer wait
  while one account's lock is held.
- **Documents:** the user guide and the UML carry the 1.0.0 version and behaviour changes.
- **Consistency:** history dates follow the shared app offset; home and caregiver
  actions use the shared language rule; course-length messages use the shared
  constant; the notification inbox trims the account hash like account deletion.

## Review corrections (2026-11-07)

- A slot-check request arriving after midnight is shown without the Taken button, a
  Taken tap on an earlier day's request removes the notification without recording,
  and reading the chat removes the request notification. The home widget updates
  right after a Taken tap.
- Medication search shows the daily-limit, sign-in and delay messages instead of a
  connection error.
- Multi-entry manual saves refresh once at the end and report duplicates separately;
  custom intervals read "Every N days" in English.
- Manual entry shows again, before saving, on which days a non-daily or custom-interval
  course creates doses and reminders, and that as-needed medicines are left out of
  scheduled and missed-dose reminders (owner decision); both wrap by word.

## Review corrections (2026-11-08)

- Chat stays reachable when the link lookup fails (collaborator change). Before the
  first lookup answers, the chat tab now follows whether this device last saw a
  connection for the account, so devices without connections no longer show the tab
  for a moment at every launch; the remembered flag is removed with the account's
  local data.

## Review corrections (2026-11-11)

- **Prescription privacy:** when a prescription table's name cell is read before its
  label, the name is now masked too. It had stayed in the text sent for analysis,
  and the server could not catch it once the label was gone (see the decision log).
- **Pill identification:** the shared connection pool of this line dropped the
  Content-Type of multipart uploads, so every pill identification answered 422. It
  now keeps the request's own headers; no released build had the defect.
- **Word wrap:** the remaining Korean messages, dialogs, descriptions, card titles,
  page titles and multi-word labels wrap between words instead of between syllables
  (`KeepWordsText`, the style chosen on 2026-11-04).
- **User guide:** four screenshots that no longer matched the app (2.3-4, 2.3-9,
  2.12-8, 7.5-5) were retaken; the others were compared with the current screens and
  kept.

## Refactor pass (2026-11-11)

Behaviour-preserving clean-up of the app and the server since the 0.2.5 pass; no
screen, text, API response or schema changed.

- Removed code with no caller: unused view-model getters, a test-only pill
  preprocessing wrapper, unread widget fields and spacing tokens.
- Values that had to agree now come from one place: the chat page size and delete
  limit, the caregiver alert and as-needed key prefixes, the 14-day schedule window,
  the skip-reason length, the default alarm time, the deleted-account and
  quota-storage error texts, and the searched-medication field lengths shared by the
  cache table, the chat attachment schema and the cache writer.
- The server's daily-budget clocks use the shared application clock.
- Fixed while surveying: the revocation cache's clean-up at 10,000 accounts (see
  Revocation check above).

## Review corrections (2026-11-12)

- **Home count after a reminder action:** a Taken action pressed while the app was
  closed opens the app, which queues the dose, but the upload was usually made by the
  background upload job that the same record starts. The app's own upload pass had
  just finished and missed the record, and nothing told the open app about the job's
  upload, so it kept the record as pending ("복용 기록 2건 전송 대기") for about a
  minute, and a schedule read crossing the upload could show the old count (2/4 for
  3/4 on the phone) until another tab was opened. Background engines now tell the open
  app when they change the dose store, and a record queued during an upload pass gets
  a pass of its own. Reproduced and checked on the emulator.
- **Doubled action:** Android handed the button that opened the app over twice (as
  the launch intent and again as a new intent), so one Taken press queued and sent the
  dose twice. The second copy of the same button within 30 seconds is now ignored; a
  reminder shown again (10 minutes at the earliest) still works.

## Review corrections (2026-11-13)

- **Today's reminder after an undo:** reminders were reconciled only when the schedule
  was read again (app start, a revisit of the schedule tab after 15 s, settings
  changes), not when a dose was recorded. A slot whose reminder for today had been
  cancelled, by a widget Taken or by a sync while it was complete, stayed without it
  after the dose was undone in the app, so that day's reminder did not ring unless the
  schedule was opened again. A dose recorded in the app now reconciles reminders at
  once (Taken drops today's reminder, undo brings it back); when the 14-day schedule
  cannot be read, nothing is rescheduled from today's schedule alone. Found and checked
  on the emulator.

## Device and operations checks (2026-11-12)

- **Devices:** the signed `6ce1d32` build (`1.0.0+27`) on the Galaxy Note10 (patient)
  and the `medbuddy_pixel7` emulator (caregiver) against production, both updated over
  0.2.5 with `adb install -r` and keeping their sign-in and data. Passed: pill
  identification (16 candidates), the mock prescription masking the name cell right
  of its label, chat both ways with push and live delivery, read notifications
  cleared, delete for everyone on the other device in about 3 s, the reminder's Taken
  action in the foreground, the background and with the app killed, the 10-minute
  snooze (exact alarms, records on the server), and the Taken button of a caregiver's
  slot-check request with the app killed (slot recorded, notification removed, the
  snoozed reminder cancelled, completion card posted). Found: the home progress card
  kept the old count after a Taken action from a killed app (fixed, see Review
  corrections 2026-11-12).
- **Firebase (owner approval):** the phone provider and SMS multi-factor
  authentication are off (the app never offered either), `localhost` is no longer an
  authorized domain, users cannot delete their Firebase account outside the app, and
  SMS is limited to Korean numbers. Left as they are: the password policy, the
  sign-up quota (100 accounts per address an hour), old anonymous accounts and one
  unattributed debug fingerprint pair.
- **Edge and repository:** the Cloudflare rule "MedBuddy API burst shield" (60
  requests per IP per 10 s, then a 10 s block) now also covers `/api/v1/pharmacy/` and
  `/api/v1/hospitals/`. The unused repository secrets `GEMINI_API_KEY` and
  `PUBLIC_DATA_API_KEY` were deleted (not rotated); `beta-android` allows
  `beta/v1.0.0`.
- **Host:** SSH accepts keys only, the pending security updates are installed, and old
  test containers and rollback images were removed. The host boots through hand-made
  systemd-boot entries pinned to one kernel: `ubuntu-sdboot-43.conf` (7.0.0-43) is the
  default and `ubuntu-sdboot.conf` (7.0.0-30) the fallback, so a later kernel update
  needs the same copy to `/boot/efi/EFI/UbuntuSD` and a new entry. `ufw` stays off
  (AdGuard serves DNS for the home LAN); remote desktop and the AdGuard admin page
  listen only on the LAN and Tailscale.
