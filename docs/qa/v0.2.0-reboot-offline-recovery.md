# Reboot and offline recovery contract

## Implemented recovery layers

1. **Native alarm persistence:** the existing Android manifest registers
   `ScheduledNotificationBootReceiver` for `BOOT_COMPLETED` and
   `MY_PACKAGE_REPLACED`, with `RECEIVE_BOOT_COMPLETED` permission. The pinned
   notification plugin persists scheduled requests and re-registers them without
   a server call. Do not add a second receiver that would duplicate this work.
2. **Foreground read recovery:** initial schedule errors and app resume trigger
   a single-flight read of schedule and alarm settings. Failed reads retry after
   5, 15, 30, 60, then 120 seconds, capped at 120 seconds while foregrounded.
   Background/disposal cancels timers; resuming during an in-flight read waits
   for it rather than starting a concurrent request. Success stops retries.
   Replacing the account's view model disposes its recovery coordinator.
3. **Protect existing alarms:** synchronization requires successful schedule AND
   alarm-setting reads. Cached settings plus a successful empty schedule response
   must not cancel alarms after a partial outage. Foreground read recovery does
   not replace native alarms or erase a pending snooze.
4. **Persistent replenishment:** the existing 12-hour network-constrained worker
   maintains the bounded 14-day reservation window within course dates. Reopening
   the same account no longer cancels/recreates its work and resets its pending
   retry. Account changes cancel the old tagged work. Explicit exponential
   backoff starts at 30 seconds; execution timing remains under Android control.

## Safety boundaries

- A notification is a reminder, not proof of ingestion. No completion is inferred
  from delivery, unlocking, rebooting, or absence of a response.
- Automatic recovery retries **reads**, never medication completion/deletion or
  caregiver/chat writes. Existing failed completion operations retain their
  failure state until explicit retry; do not claim that an offline write synced.
- A durable offline completion outbox is **not implemented here**. It requires
  account-scoped encrypted persistence, operation IDs, original dose dates,
  idempotent backend handling, conflict/undo semantics, and visible pending vs
  server-confirmed status before it can be enabled safely.
- This is not a complete offline cache of all screens. A first offline launch
  may still need connectivity for authentication or uncached server data.
- Existing scheduled alarms survive outages only within the reservation/course
  window. A prolonged outage cannot safely invent future medication schedules.
- Reboot support is **after the first PIN unlock**. Credential-encrypted storage
  is unavailable before that; direct-boot health-data storage is deliberately
  not introduced. A powered-off device cannot notify. Overdue alarms may be
  delivered late by Android; stale-day completion actions remain rejected.
- Android force-stop, notification permission denial, exact-alarm permission
  changes, and OEM battery restrictions are distinct from ordinary process death.
  Do not promise exact delivery while the OS prevents it.

## Verification

Automated regressions cover foreground backoff, stop/resume/dispose, concurrent
request prevention, partial endpoint failure, reconnect success without writes,
and preservation of native alarms when background network reads fail. Manifest
checks guard the existing boot receiver/permission configuration. These are not
substitutes for physical reboot evidence.

### Physical gate: reboot

Use a clearly labelled, one-day dummy fixture with no linked caregiver. Preserve
real records and record the original phone settings. **Use USB ADB or a separately
verified post-reboot connection route first**; temporary TCP ADB on port 5555 is
not a guaranteed reboot recovery route.

1. Install the exact checksum-verified signed revision as an update.
2. Schedule a dummy alarm sufficiently after reboot and record its Android ID,
   timestamp, channel/group metadata, and the baseline of unrelated alarms.
3. Reboot; unlock once using the PIN, but do not launch MedBuddy.
4. Confirm Android restored the pending alarm and later posts the notification.
5. Launch the app, verify session/state and inbox recovery, and verify cancelling
   only the dummy slot removes its delivered notification.
6. Remove only test fixtures/settings/inbox entries and restore phone settings.

### Physical gate: offline/reconnect

Use USB ADB so airplane mode does not sever the test-control connection. Do not
take the shared production backend offline or add permissive security bypasses.

1. Schedule a labelled dummy reminder while online; capture unrelated alarms.
2. Disconnect Wi-Fi and cellular; verify the already-scheduled native reminder
   still fires without the server. Do not mark any real medication taken.
3. Open/refresh the schedule and verify failure is not shown as successful sync.
4. Restore connectivity without restarting the app. Verify read recovery within
   the retry interval plus request latency; verify no duplicate completion writes.
5. Repeat background -> reconnect -> resume, and account-switch/disposal checks.
6. Restore network settings and remove only test-owned data.

Reboot and physical network isolation remain unverified until this protocol runs
with a recoverable device-control connection. No production outage is needed.
