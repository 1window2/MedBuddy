# Reboot and offline recovery contract

## Implemented recovery layers

1. **Native alarm persistence:** the existing Android manifest registers
   `ScheduledNotificationBootReceiver` for `BOOT_COMPLETED` and
   `MY_PACKAGE_REPLACED`, with `RECEIVE_BOOT_COMPLETED` permission. The pinned
   notification plugin persists scheduled requests and re-registers them without
   a server call. Do not add a second receiver that would duplicate this work.
2. **Foreground read recovery:** initial schedule errors and app resume trigger
   a single-flight read of schedule and alarm settings. Failed reads retry after
   5, 15, 30, 60, then 120 seconds, capped at 120 seconds while foregrounded.
   Background/disposal cancels timers; resuming during an in-flight read waits
   for it rather than starting a concurrent request. Success stops retries.
   Replacing the account's view model disposes its recovery coordinator.
3. **Protect existing alarms:** synchronization requires successful schedule AND
   alarm-setting reads. Cached settings plus a successful empty schedule response
   must not cancel alarms after a partial outage. Foreground read recovery does
   not replace native alarms or erase a pending snooze.
4. **Persistent replenishment:** the existing 12-hour network-constrained worker
   maintains the bounded 14-day reservation window within course dates. Reopening
   the same account no longer cancels/recreates its work and resets its pending
   retry. Account changes cancel the old tagged work. Explicit exponential
   backoff starts at 30 seconds; execution timing remains under Android control.

5. **Durable completion writes:** individual/whole-slot completion, undo and the
   patient chat quick reply write to an account-scoped SQLite outbox before
   reporting local success. Payloads and the same-day schedule cache use AES-GCM;
   the key is held by the platform secure store. A network-constrained one-off
   WorkManager task drains the queue; a 15-minute periodic job repairs missed
   scheduling, while foreground retries use 5/15/30/60/120-second backoff.
   Android, not the UI, decides the actual background execution time.

## Safety boundaries

- A notification is a reminder, not proof of ingestion. No completion is inferred
  from delivery, unlocking, rebooting, or absence of a response.
- Automatic write retry applies only to explicit dose records in the durable
  outbox. Ordinary chat, deletion and unrelated mutations are not queued.
- The home/schedule shell and chat display `전송 대기` until a validated server
  receipt arrives. Failed local persistence is an error, never a successful record.
- SQLite leases serialize foreground/background sending. Operation IDs remain
  unchanged after a timeout or restart; server receipts, dose changes, optional
  chat and alert outbox commit together. A retry after an undo never reapplies
  the original completion. An undo is another ordered set-state operation.
- Original dates are mandatory. Delayed records up to 30 days old are stored
  on that original day, without changing today's legacy state or generating a
  fresh caregiver completion alert. Future/older dates and removed/changed
  medication slots are rejected and remain visible as `확인 필요`.
- A rejected entry pauses subsequent queued changes until retried or explicitly
  removed from the pending-record view. Unacknowledged entries cannot be deleted:
  the server may already have saved them. Use an ordered undo instead.
- Across devices, successful explicit set-state operations use server arrival
  order; this is not a multi-device merge of competing clinical records.
- Sign-out suspends the worker; an account change cannot claim another account's
  records. Signing back into the same account resumes them. Account deletion
  removes that account's cache/queue and cascades server receipts. Android backup
  is disabled so ciphertext is not restored without its device-bound key.
- The client dose day defaults to the service's Asia/Seoul calendar (UTC+09:00),
  independently of device display timezone. A deployment changing server timezone
  must also configure `APPLICATION_UTC_OFFSET_MINUTES`; DST regions need a named
  timezone implementation before deployment.
- This is not a complete offline cache of all screens. A first offline launch
  may still need connectivity for authentication or uncached server data.
- Existing scheduled alarms survive outages only within the reservation/course
  window. A prolonged outage cannot safely invent future medication schedules.
- Reboot support is **after the first PIN unlock**. Credential-encrypted storage
  is unavailable before that; direct-boot health-data storage is deliberately
  not introduced. A powered-off device cannot notify. Overdue alarms may be
  delivered late by Android; stale-day completion actions remain rejected.
- Android force-stop, notification permission denial, exact-alarm permission
  changes, and OEM battery restrictions are distinct from ordinary process death.
  Do not promise exact delivery while the OS prevents it.

## Verification

Automated regressions cover foreground backoff, stop/resume/dispose, concurrent
request prevention, partial endpoint failure, reconnect success without writes,
and preservation of native alarms when background network reads fail. Manifest
checks guard the existing boot receiver/permission configuration. These are not
substitutes for physical reboot evidence.

The dose outbox tests use a real temporary SQLite database and AES-GCM. They
cover reopen/decryption, account isolation, foreground/background leases, ordered
taken/undo replay after midnight, rejected records and stale cache responses.
Backend tests cover receipt deduplication, transaction rollback, date/ownership
validation and atomic chat receipts. The full suites passed on 2026-09-21:
863 Flutter tests;
518 backend tests, 2 skipped (plus 21 subtests). Static analysis reported no issues.

Both Android demo emulators received the updated build. With only the patient
emulator's backend connection removed, terminating and reopening the app restored
the cached same-day schedule and its existing 1/5 completion count. Connectivity
was restored afterward. No existing medication was marked taken for this check.
This verifies cache restoration, not physical-device background write delivery.

### Known limitation: caregiver previews without alerts

The monitoring API omits schedule totals when every caregiver alert for a linked
patient is disabled. The home/widget preview currently consumes that response as
an empty schedule, although the patient's detail endpoint returns the actual
doses. This was reproduced with a second local demo patient on 2026-09-21.
Enabling a dose-completed alert allows the current preview to load, but is only
a demo workaround. Preview reads must be decoupled from alert preferences before
claiming support for patients with all alerts disabled.

### Physical gate: reboot

Use a clearly labelled, one-day dummy fixture with no linked caregiver. Preserve
real records and record the original phone settings. **Use USB ADB or a separately
verified post-reboot connection route first**; temporary TCP ADB on port 5555 is
not a guaranteed reboot recovery route.

1. Install the exact checksum-verified signed revision as an update.
2. Schedule a dummy alarm sufficiently after reboot and record its Android ID,
   timestamp, channel/group metadata, and the baseline of unrelated alarms.
3. Reboot; unlock once using the PIN, but do not launch MedBuddy.
4. Confirm Android restored the pending alarm and later posts the notification.
5. Launch the app, verify session/state and inbox recovery, and verify cancelling
   only the dummy slot removes its delivered notification.
6. Remove only test fixtures/settings/inbox entries and restore phone settings.

### Physical gate: offline/reconnect

Use USB ADB so airplane mode does not sever the test-control connection. Do not
take the shared production backend offline or add permissive security bypasses.

1. Schedule a labelled dummy reminder while online; capture unrelated alarms.
2. Disconnect Wi-Fi and cellular; verify the already-scheduled native reminder
   still fires without the server. Do not mark any real medication taken.
3. Open/refresh the schedule and verify failure is not shown as successful sync.
4. Mark a dummy dose taken while offline; verify immediate local state and the
   pending banner. Restart the app and verify both survive. Undo while still
   offline, reconnect and confirm the server's final state is not taken.
5. Restore connectivity without restarting the app. Verify receipt-driven removal
   of the pending banner and no duplicate completion writes. Repeat while the app
   is backgrounded to exercise WorkManager, allowing OS scheduling delay.
6. Repeat across midnight: the old day's record must not check today's dose.
   Try a removed medication and verify review state, not silent loss or endless retry.
7. Repeat background -> reconnect -> resume, and account-switch/disposal checks.
8. Restore network settings and remove only test-owned data.

Reboot and physical network isolation remain unverified until this protocol runs
with a recoverable device-control connection. No production outage is needed.
