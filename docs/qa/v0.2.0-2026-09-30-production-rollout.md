# September 30 v0.2.0 production rollout evidence

The deployed source is reviewed `beta/v0.2.0` commit `16191b2`. This rollout
does not publish v0.2.0 or approve public distribution.

## Backup and migration rehearsal

- Before changing the live backend, a private PostgreSQL custom-format backup
  was retained on the production host as
  `medbuddy-before-v020-20260930T052303Z.dump` (963,965,908 bytes; SHA-256
  `5061c8c66a1427e32d764df899a1c92c3fe93db5fe4d3868d4eb2a6a042a13fa`).
  The archive inventory passed `pg_restore -l`. The backup was not copied to
  the repository.
- The backup restored successfully to an isolated temporary PostgreSQL
  database. Its Alembic revision (`c2a7e4d9f610`) and sampled row counts
  matched the production snapshot: saved medications 11, medication
  completions 11, chat messages 0, pill references 25,426, and pharmacy
  catalog records 25,442.
- A second isolated restore was migrated using the new production migration
  image from `c2a7e4d9f610` to `b3a7d9e2f601`. The same sampled counts were
  preserved; new dose-sync, pharmacy-cache, and chat-notification tables were
  initially empty as expected. Both disposable rehearsal databases were
  removed after verification; the retained private backup can recreate them.

## Live rollout and checks

- The production checkout fast-forwarded to `16191b2`; its pre-existing
  untracked QA note was left untouched. The old backend and catalog-refresh
  containers were stopped for a coordinated Compose rollout. The one-shot
  database migration and catalog bootstrap succeeded, and all five long-running
  services were healthy or running afterward.
- Live `alembic current` reports `b3a7d9e2f601 (head)`. Local core `/ready`
  reports production API/Firebase readiness and `app_check_required: false`.
  Local and public `/ready/catalogs` return JSON HTTP 200. This readiness
  endpoint checks presence, not catalog completeness or freshness.
- The credential-free public ingress gate passes pharmacy, hospital, and chat:
  each protected route reaches FastAPI authentication. An unknown API route
  remains Cloudflare-blocked with HTML HTTP 403. No authenticated records were
  written for these probes.
- Production catalog counts at rollout were 25,426 pill references and 25,442
  pharmacy records. Their latest stored update timestamps were September 24;
  reconcile the current KPIC floor before release.
- A bounded, fixed-coordinate hospital location request from the production
  backend failed. The upstream national hospital API returned HTTP 403 and XML
  reason code `30`; the public-data portal documents code `30` as an
  unregistered service key. The production backend has no hospital-specific
  key configured and falls back to its shared public-data key. A KASI holiday
  lookup with that shared key succeeded, so investigate hospital-service
  registration/approval and key scope before changing application code. No
  credentials or hospital response body were recorded.

## Backend update — 2026-10-07

The owner authorized updating the live backend over SSH. The host was running
`16191b2` from September 30. Between that revision and `85e9843` there are no
migration, dependency, environment or Compose changes other than the uvicorn
proxy trust list.

- Before the update the existing backup script wrote a private custom-format
  dump on the host, `medbuddy-postgres-20261007T082845Z.dump` (962,933,141
  bytes; SHA-256
  `83da60bd66046f1a8d7cbbc5c9eccd066c1591482ff310f6c5ba054a4365084f`), and its
  `pg_restore --list` check passed. The four previous images were tagged
  `rollback-16191b2`.
- The checkout was fast-forwarded to `85e9843` and the documented
  `docker compose ... up -d --build --wait` command completed. `database-migrate`
  and `catalog-bootstrap` exited 0; backend, catalog refresh, PostgreSQL, Redis
  and the tunnel reported healthy. Alembic remained at `b3a7d9e2f601`.
- Sampled row counts were identical before and after: saved medications 12,
  medication completions 12, chat messages 0, dose-sync operations 6, user
  accounts 5.
- Local and public `/ready` returned HTTP 200 with contract `medbuddy-api-v1`,
  `production`, `api`, `firebase`, project `medbuddy-26` and
  `app_check_required: false`; public `/ready/catalogs` returned 200. Pharmacy
  and chat routes without credentials returned JSON 401 and an unlisted path
  stayed blocked by Cloudflare with HTML 403. No error, traceback or exception
  line appeared in the backend log after startup.
- Proxy trust: the running command now carries the private-range
  `--forwarded-allow-ips` list. Two unauthenticated requests sent through
  Cloudflare with a forged `X-Forwarded-For` value were counted in Redis under
  the caller's real address as reported by Cloudflare, and no quota key was
  created for the forged address.

This deploys the chat-linked dose route correction, the dose-receipt purge on
account deletion, the deleted-user token response and hidden SQL parameters.
Those four were not exercised against production with a real account; they
are covered by automated tests. App Check enforcement is unchanged and still
disabled under the off-Play exception: the server and the `beta-android`
environment both report `false`, and the Play signing fingerprint, release
distribution policy and read-only preflight identity are not configured.
