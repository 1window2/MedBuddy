# v0.2.0 offline dose date-boundary review

Baseline: `1da4dfb`, existing `beta/v0.2.0`, September 22, 2026.

## Immediate priority

The recent commits added chat intake recording, an encrypted offline write
queue, idempotent server receipts, and an Android dose widget. Correctness of
those medication-state writes takes priority over additional UI features.
This review is focused, not blanket release approval.

## Confirmed defect and correction

A foreground schedule or summary request could start before application
midnight and finish afterward. The cache previously assigned the date when
processing the response, so yesterday's schedule could appear as today's.
The in-memory date was also recalculated after asynchronous persistence,
allowing a second midnight race to enable default current-day dose writes.

- Capture the application day before each foreground read and reject a
  response if the day changes, including during cache/widget publication.
- Require the caller's request day when caching a schedule. Validate it after
  initialization, and retain it in both persistent and in-memory snapshots.
- Pass the widget's already captured request day through the same contract.
- Keep historical queued dose operations unchanged; their explicit original
  dates are intentional and must not be reassigned to today.

This strengthens the existing ViewModel -> DoseSyncService -> DoseOutboxStore
boundary documented in `docs/UML/class/06_DoseSyncAndWidget.puml` and
`docs/UML/sequence/OfflineDoseSync.puml`; no new architectural layer is added.

## Verification

Regression coverage uses mock HTTP, an injected clock, real SQLite and real
encryption, without production accounts or medication writes. Cases cover both
foreground read paths, initialization, persistence, publication, rejected
new-day writes, and recovery on an explicit fresh read.

Validation uses Flutter 3.41.5 (the CI version) in an isolated frontend copy.
The full Flutter suite passed **868 tests**, and full static analysis reported
**no issues**. `git diff --check` also passed. Backend code is unchanged.
The committed lockfile cannot be used unchanged with that SDK: resolution
changes nine packages, including `meta`, `test_api` and the SQLite family.
Normal `flutter pub get`, as currently used by CI, resolves this; the repository
lockfile is deliberately untouched by this focused fix. Aligning the supported
SDK and lockfile, then enforcing it in CI, remains a reproducibility follow-up.
