## Defects corrected in this review

### Chat transport could block or fail already-persisted operations

Broadcast previously awaited each socket serially without a deadline. A stalled
client could delay healthy recipients and the REST response indefinitely.
`WebSocketDisconnect` also escaped the existing exception handler. Connection-limit
rejection awaited a transport close while holding the process-wide registry lock.

The manager now sends independently with finite deadlines, catches expected
disconnect failures, removes failed recipients before presence-based push fallback,
and bounds close operations outside the registry lock. Existing link/recipient
scoping is preserved. Each send and cleanup close has a five-second deadline.
This is best-effort transport; persisted history remains the recovery source.

### Completion outbox lost the original dose date and live-state meaning

Completion writers hashed the dose date into the event key but left the existing
`schedule_date` column empty. Processing used today's chat context, so a retry
after midnight could reinterpret an earlier event. Delivery also did not recheck
whether a dose had been corrected or deleted after enqueueing.

Both completion writers now persist the captured dose date in the transaction.
Before chat publication or FCM dispatch, the processor requires the current
application date and a nonempty, still-complete active slot. Invalidated events
become terminal `dead_letter` rows with a diagnostic reason and are counted as
skipped, without a sent timestamp. Existing undated queued completion events are
also suppressed: their date is not guessed. No schema migration is needed because
the nullable date column already exists. This deployment behavior must be included
in the backend rollout review; medication records are not modified by suppression.

Tests cover stale/future/undated events even when today's dose is complete,
corrected/deleted doses, current-date success, partial-delivery retries and retry
exhaustion. Delivery is still at least once; this does not recall notifications
already delivered or guarantee serialization against a correction racing with FCM.

## Architecture assessment

The existing Boundary-Control-Entity structure remains suitable for the current
single-process beta. Keep completion policy in the schedule control, transaction
and retry policy in the outbox processor, and transport failures in the connection
manager. No broad rewrite or parallel medication writer is warranted.

Constraints to preserve:

- Chat connections and live event fan-out are process-local. Multiple API workers
  require shared fan-out and presence before scaling; shared Redis quotas alone
  do not provide that functionality.
- Chat push uses in-process background work, unlike the durable caregiver outbox.
  If durable chat notification delivery becomes a requirement, it needs its own
  persisted event workflow. Chat history itself is already persisted.
- Foreground recovery retries reads, not completion/deletion writes. Durable
  offline completion requires original dates, idempotency, account-scoped secure
  persistence and conflict semantics; it is not implemented.
- Completion is an explicit user record. Recognition or notification receipt must
  never silently create it.
