# 약 등록 검토와 저장 경계

이 문서는 `bbbdef53` 이후 v1.0.1에서 바뀐 알약·직접 입력·처방 결과 흐름을
설명한다. 사진 후보는 진단이나
실제 약의 확정 식별이 아니며 사용자가 포장 또는 전문가와 확인해야 한다.

## 선택과 일정 검토

- `PillIdentificationUI`는 미저장 항목 중 후보를 선택한 항목만 다음 단계로 보낸다.
  선택이 0개이면 계속할 수 없고, 같은 후보를 다시 눌러 미저장 선택을 해제할 수 있다.
  선택한 알약마다 앞면 사진과 확정된 후보가 있어야 하며, 표시된 목록 밖에도 비슷한 약이
  있다는 안내(`hasMoreCandidates`)가 남은 알약이 선택에 있으면 뒷면을 추가해 후보를
  좁힐 때까지 계속할 수 없다.
  후보 없음·실패·미선택 항목을 임의로 채우거나 저장하지 않는다. 하단 동작은 선택
  개수를 표시하며, 일부 선택도 허용한다.
- 같은 품목의 여러 사진은 각각 유지하거나 동일 일정끼리 묶도록 사용자에게 묻는다.
  일정 검토 뒤 `ResolveDuplicatePillSelectionControl`이 확인된 품목과 일정이 같은 요청만
  합친다. 같은 품목이라도 일정이 다르면 별개다.
- `MedicationScheduleReviewUI`는 선택된 약의 용량·기간·시작일·시간대와 주기를
  편집 가능한 카드로 표시한다. 초기 제안값은 사용자의 확인 대상이지 처방 추천이
  아니다. '확인하고 계속하기'는 저장 명령이 아니다.
- `ManualMedicationEntryUI`도 유효한 입력을 공통 결과 단계에 넘긴다. 최대 10개,
  정기/필요시 구분, 사용자 지정 1~90일 간격, 선택 품목과 이름의 일치 검사는 유지한다.

## 사진 보기

`MedicationReviewImageGallery`와 `showMedicationReviewPhotos`는 알약 일정 검토의
앞·뒷면/관찰 영역 사진, 처방 OCR 미리보기, 약 사진 확대에서 같은 중앙 모달을
사용한다. 썸네일로 사진을 고르고 최대 5배까지 확대한다. 원배율의 한 손가락 가로
이동만 사진 넘김으로 처리하고 확대 중에는 이미지 이동으로 처리한다. 사진을 바꾸면
배율과 이동을 초기화한다. 사진 비율, 제목, 닫기, 설명 영역은 분리하며 OCR 화면은
기존 인식 표시·민감정보 마스킹을 유지한 캔버스를 전달한다. 모달 재사용이 새 분석이나
사진 업로드를 발생시키지는 않는다.

## 공통 결과와 저장

`MedBuddySavedMedicationFacade`는 검토 입력의 변경 불가능한 사본을 만들고
`MedBuddyPrescriptionViewModel.showMedicationRegistrationResults`에 전달한다.
이 메서드는 유효한 idle 상태에서만 입력을 수락한다. 수락 후에만 등록 경로를 닫아
홈이 소유한 `CheckResultUI`를 보여준다. 화면에는 `MedicationResultSource`에 따라
처방 분석·알약 등록·직접 등록 제목을 구분한다. 알약·직접 등록은 전체 처방으로
취급하지 않으며 처방 변화 레이더를 조회하지 않는다.

개별 저장 또는 전체 저장을 눌러야 해당 경로의 기존 저장 기능을 호출한다.
전체 저장은 미완료 항목을 순차 시도하며 성공·중복 항목은 완료 상태로 유지하고
실패 항목만 재시도한다. 저장 완료 뒤 목록·일정·알림 갱신이 실패해도 이미 저장된
행을 다시 저장 대상으로 바꾸지 않는다. 전체 원자적 저장이나 재시작 복원 큐는 아니다.
콜백을 직접 주입한 독립 등록 화면의 기존 직접 저장 경로는 호환용으로 남아 있다.

모든 항목이 저장 또는 중복 완료되면 중앙 완료 대화상자에서 오늘 일정·복약함·홈을
선택할 수 있다. 대화상자를 먼저 닫고 목적지로 이동한다. 일부 실패는 결과 화면에
남긴다. 결과에서 나가기 확인은 저장한 약을 유지하고 미저장 입력은 폐기한다고 안내한다.
계정·결과 세대가 바뀌면 늦은 조회 뒤 새 저장이나 사진·일정 후속 처리를 시작하지
않는다. 이미 서버가 수락한 저장을 취소하는 계약은 아니다.

직접 입력의 임시 사진은 결과 단계가 수락했을 때 소유권을 넘겨받는다. 저장 성공 뒤
약 ID별 기기 사본을 만들고, 결과 종료·폐기 때 사용하지 않는 앱 임시 사본을 정리한다.
저장 중인 사진 정리는 요청 종료까지 미룬다. 사진 보관 실패가 서버 저장을 되돌리거나
원본 사용자 파일을 삭제하는 것은 아니다.

## 선택 품목 저장과 지연 보완

알약 저장은 이름 재검색 대신 `GET /api/v1/medication/catalog/{item_seq}`로
정확한 로컬 품목을 조회한다. 앱은 최대 5초를 기다리며 응답 품목이 다르거나 조회가
실패하면 선택 후보와 확인한 일정으로 저장한다. 이 5초는 전체 저장 시간의 보장이
아니다. 직접 입력의 미선택 이름 조회와 처방의 후보 확인 경로는 그대로 유지한다.

서버는 `/save`의 저장·중복 결과를 확정한 뒤 `saved_medication_enrichment`를 통해
누락된 효능·사용법·주의·상호작용·부작용·보관 정보 보완을 최선 노력으로 예약한다.
로컬 자료, 이름 키 캐시와 공공 API에서 **같은 품목번호의 단일 결과**만 사용한다.
공공 어댑터의 이름 검색을 이용하더라도 다른 품목으로 대체하지 않는다. 선택적인
요약 실패 시 읽을 수 있는 원문을 사용할 수 있다.

보완은 요청 DB 세션과 분리된 작업이며 적용 직전 계정 삭제 상태, 소유자·품목·약 ID,
처방 revision과 일정 필드, 중단·교체 여부, 원래 누락 값이 그대로인지 재검사한다.
사용자가 채운 값·복용량·일정·이름을 덮어쓰지 않는다. 이벤트 루프별 최대 32개 작업,
동시 2개와 대기 포함 40초 조회 제한을 사용한다. 영속 작업 큐가 아니므로 프로세스
종료·포화·시간 초과 후 보완 완료를 보장하지 않으며 저장 성공도 되돌리지 않는다.
다음 목록 조회에서 보완된 정보를 볼 수 있지만 별도 실시간 갱신 보장은 없다.

정확 조회의 파싱·길이 제한과 식별 시간 초과 진단은
[약명 매칭 문서](Medication%20Matching%20Review.md), 전체 흐름은
[등록·보완 시퀀스](UML/sequence/MedicationRegistrationReview.puml)를 따른다.
